Fuente: src/waapi/waapi.js:186-540. waapi.animate(targets, params) crea animaciones nativas (el.animate) por propiedad; convierte cualquier easing de Anime a linear() muestreado (easingToLinear, :85, 100 puntos; un muelle usa su settlingDuration, :288); y las transformadas individuales (x, rotateY, scale...) las anima como custom properties registradas (CSS.registerProperty('--translateX'), :195-215) con transform: translateX(var(--translateX)) ... puesto en el elemento (:349-355). persist (:257), commitStyles() (:464), composition → composite (:290), y tl.sync(waapiAnim) la mete en una timeline animando su currentTime desde JS (timeline.js:268-287).

Pregunta aislada: pulsa «ocupar el hilo» y luego «lanzar». Con el hilo bloqueado, ¿cuáles siguen fluidas? Lo que se espera por lectura: 1 y 2 sí (el compositor anima transform); 3 quizá no (una custom property que alimenta transform se resuelve en el hilo principal, ⚠ sin verificar); 4 no (JS); 5 no (la timeline empuja currentTime desde JS). Es LA medida que decide cómo se escribe el vuelo del libro.

1 · WAAPI nativa: el.animate([{transform}], …)

2 · waapi.animate(el, { transform: 'translateX(640px) rotate(180deg)' }) (la propiedad entera, string)

3 · waapi.animate(el, { x: 640, rotate: 180 }) (transformadas individuales → custom properties)

4 · animate(el, { x: 640, rotate: 180 }) (motor JS, rAF)

5 · waapi.animate dentro de createTimeline().sync() (JS empuja currentTime)

Qué mirar

El medidor vive en el hilo principal: con el hilo ocupado marcará perdidos aunque las cajas 1 y 2 vayan finas. Mira las cajas, no la cifra. Si la 3 se atasca, la consecuencia para el libro es concreta: el vuelo se escribe con transform entero como string (o con el.animate directo), no con x/rotateY sueltos; y la timeline de Anime orquesta (tiempos, etiquetas, scrubber) pero no puede ser quien mueva cada fotograma si se quiere el compositor.
